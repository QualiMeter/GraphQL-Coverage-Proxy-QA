## Самостоятельный бизнес-API

`tests/api/shop/test_business_rules.py` содержит 16 сценариев, каждый выполняется по двум HTTP-транспортам: direct и proxy (32 проверки). Сервис `examples/shop/api` использует отдельную PostgreSQL. Тесты проверяют каталог и пагинацию, авторизацию, роли и частичные ошибки, сохранение профиля, заказ нескольких товаров, атомарность отказа, чужие заказы, idempotency key, конкуренцию двух покупателей и сохранение данных после перезапуска API. Ожидания денежных сумм и остатков вычисляются из исходного каталога; успешный ответ mutation проверяется отдельными query.

`test_business_field_coverage` проверяет точные поля настоящего бизнес-запроса через Coverage API. Знаменатель берётся из независимого разбора опубликованной SDL бизнес-сервиса. У этой схемы 35 полей, а не 10 полей диагностической фикстуры. Оба стенда имеют разные назначения: компактная фикстура проверяет контролируемые сбои прокси; бизнес-сервис — транзакционные правила и пользовательские сценарии.

## Публичный сервер

`tests/live/test_deployment.py`: GET /health, /openapi.json, /api/services, /api/schemas и граф, неизвестный run. Никакие сервисы, прогоны или заказы на публичном сервере не создаются. Эти 4 smoke-проверки доступны только при явном --live-base-url; они не доказывают корректность всех защищённых production-операций.

## Наглядный мини-магазин

`examples/shop/web/` — самостоятельная витрина FORMA с корзиной, входом, заказами, профилем и API-инспектором. Десять Playwright-сценариев в `tests/e2e/test_shop.py` проверяют:
1. Каталог, поиск, наличие и корзину без преждевременного списания.
2. Создание и отмену реального заказа с независимым чтением БД через API.
3. Ошибку входа и маскирование секретов (`<скрыто>`) в API-инспекторе.
4. Административный кабинет с живой аналитикой.
5. Задержанный ответ заказов после выхода (очистка состояния при logout).
6. Повтор покупки после потери ответа 502 с сохранением idempotency key и однократным списанием остатков.
7. Временный отказ 503 при восстановлении профиля (сохранение сессионного токена).
8. 504 Gateway Timeout каталога, отображение индикатора «Нет связи с API» и восстановление витрины по кнопке «Попробовать снова».
9. Полный обрыв сети (сетевой drop / abort) при покупке, сохранение корзины и успешный заказ после восстановления соединения.
10. Каскад ошибок 502/504 при многократных перезагрузках страницы без потери авторизации покупателя.

Браузерный трафик этих тестов действительно проходит через Coverage Proxy с отдельным run ID. Серверные ключи остаются на BFF; снимки покрытия сохраняются в общих артефактах тестового проекта.


## Панель управления

Каталог формируется pytest collection. Проверки `tests/platform/test_panel.py` подтверждают отказ неавторизованных локальных команд и чужого origin, запрет неизвестных тестов/путей, чтение истории и доказательств, запрос отмены, реальный запуск выбранного pytest-сценария и сохранение статуса cancelled. В интерфейсе проверены выбор сценария, запуск, отображение результата, поля и история. Живые данные пишутся самим pytest в progress.json и live/; процент выполнения выводится из завершённых выбранных сценариев, а не из таймера.

## Ограничения текущего контракта

- Метрика описывает выбранные поля запроса при успешном анализе и объекте data. Частичный ответ с errors может учитываться; тест не объявляет это успешным исполнением каждого резолвера.
- Named/inline fragments поддерживаются анализатором. QA проверяет точные координаты и hits, вложенные повторы, aliases и @include с true/false. Неизвестные и циклические fragments должны давать validation_error без покрытия. Subscription остаётся unsupported; отдельный тест и смешанная статистика проверяют это независимо от fragments.
- Сетевые ошибки и таймауты не записываются текущим обработчиком как ObservedRequest. Тест фиксирует контракт, а не придумывает запись.
- Список `/requests` не содержит selectedFields; detail `/requests/{requestId}` содержит фактические поля и countedInCoverage. Отчёт сохраняет оба уровня и сопоставляет HTTP-вызов с detail только при однозначной связи. `declaredSelectedFields` остаётся независимым ожиданием, а не измерением.
- Связь с pytestNodeId хранится в metadata прогона и артефактах тестов; новые колонки БД не добавляются.
- Multi-service проверяется двумя настоящими upstream с разными ответами. Проверяются опасные URL и отсутствие обхода endpoint через introspection payload. Полный DNS-rebinding/SSRF/resource-limit аудит остаётся за специализированными тестами backend.
- Cookie-сессии viewer/analyst/operator, CSRF, grants, отзыв grant, скрытая metadata и logout проверяются по HTTP. TLS/Secure-cookie через production Nginx, last-admin и конкурентные security races остаются в специализированном наборе backend. Основной frontend этим набором не открывается.

Тесты не изменяют командный backend/frontend. Тестовый upstream и HTML для одного E2E находятся в `tests/support/upstream/`; бизнес-API и витрина — в `examples/shop/`.

Тесты используют независимые ожидания DTO и бизнес-результатов. Статистика сверяется с реальными durations журнала; P95 вычисляется линейной интерполяцией в тесте. Код анализатора, ORM и функции API backend не импортируются.

## Дополнительные сценарии реальных сбоев

- `test_public_service_does_not_publish_private_evidence`: анонимный клиент читает опубликованный граф и историю, но не журнал/detail/служебную metadata/endpoint. После снятия публикации чтение снова закрыто без утечки total.
- `test_login_rotates_and_revokes_previous_cookie`: повторный вход меняет токен и отзывает старую cookie. Отдельно проверяются реальные HttpOnly/SameSite cookie-атрибуты и работа новой сессии. Значения токенов в проверки ожидания/факта не выводятся.
- `test_storefront_retry_after_lost_checkout_response`: Playwright пропускает mutation до настоящего BFF/proxy/API, после успешного commit подменяет только браузерный ответ на 502. Повтор из той же корзины обязан использовать исходный idempotency key. Независимое чтение API подтверждает один новый заказ и одно списание товара. Fixture отменяет свой заказ после теста.

Последний сценарий не подменяет успешный бизнес-ответ: оба вызова обрабатывает реальный commerce API с PostgreSQL. Ошибка внедряется между уже выполненной сервером mutation и браузером, чтобы воспроизвести неоднозначный для клиента результат сети.
