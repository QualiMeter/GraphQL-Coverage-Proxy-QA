# Как добавлять свои API-тесты

Пишите Python-код в `tests/api/shop/test_<тема>.py`. Имя функции начинается с `test_`. Декоратор `@pytest.mark.case("Название")` задаёт название в панели и отчёте. Любой файл test_*.py из этой папки автоматически включается в business и all.

Готовый учебный пример — `tests/api/shop/test_order_filters.py`: создать заказ → отменить → независимо запросить CANCELLED и CREATED → проверить, что фильтры соответствуют сохранённому состоянию.

## Минимальная структура

```python
import pytest

@pytest.mark.case("После входа виден свой профиль")
def test_my_profile(business):
    b = business
    response = b.gql("Получить профиль", "{ me { id email } }")
    b.api.expect("Пользователь определён правильно", response["data"]["me"]["id"], "alice")
```

`business` — готовая pytest-фикстура. Она запускает изолированное окружение, выполняет вход Alice и повторяет вашу функцию дважды: direct и proxy. В proxy-варианте также создаёт прогон покрытия и сохраняет серверные поля/наблюдения. Схема API — `examples/shop/api/schema.graphql`, правила — `examples/shop/api/README.md`.

## Основные методы

| Вызов | Результат |
|---|---|
| b.gql(название, query, variables) | Полное тело GraphQL-ответа. Проверяет HTTP 200 и отсутствие errors |
| b.catalog() | Список товаров с id, priceCents и stock |
| b.create([{productId, quantity}]) | Созданный Order; ключ идемпотентности генерируется автоматически |
| b.read_order(id) | Полное тело GraphQL-ответа отдельного query |
| b.cancel(id) | Полное тело GraphQL-ответа отмены |
| b.login("bob") | Меняет текущую сессию на Bob; можно также использовать admin |
| b.api.expect(название, факт, ожидание) | Проверка равенства с ожиданием/фактом в отчёте |

Обычный `assert` тоже работает, но `expect` делает сравнение наглядным в панели. Названия шагов объясняйте действием: «Получить остаток», «Оформить заказ», «Перечитать заказ».

## Ожидаемая ошибка

```python
body = b.create([{"productId": "cable", "quantity": 0}], errors=True)
b.api.expect(
    "Сервер отклонил нулевое количество",
    body["errors"][0]["extensions"]["code"],
    "BAD_USER_INPUT",
)
```

Для произвольного запроса с ожидаемыми errors используйте `b.gql(..., errors=True)`. Не ограничивайтесь HTTP 200: GraphQL может вернуть его вместе с errors и data=null.

## Данные и очистка

Заказы, созданные через `b.create`, отменяются в cleanup фикстуры, в том числе при падении теста. Удаления истории API не поддерживает: отменённые заказы остаются в БД. Поэтому ищите конкретный ID, а не ожидайте, что список всегда состоит из одной записи. Изменение профиля восстанавливайте своим try/finally.

Для суммы/остатков сначала прочитайте каталог, вычислите ожидаемое изменение и сравните его с отдельным query после mutation. Не копируйте фактический ответ в ожидаемый и не проверяйте сохранение только ответом той же mutation.

## Запустить свой сценарий

Из корня QA checkout, при работающем Docker:

```powershell
.\.venv\Scripts\coverage-qa test --suite business --local -- -k cancelled_order_filter
```

Будут выполнены direct и proxy варианты. Все отчёты получат новые ID.

Через панель: сохраните файл → нажмите **«Обновить список»** в блоке «Сценарии» → найдите название → отметьте нужные варианты → **«Запустить тесты»**. Во время активного прогона обновление каталога недоступно. Если код содержит ошибку импорта или синтаксиса, панель покажет ошибку сбора pytest; исправьте файл и повторите обновление.

Отдельные тесты самого Coverage Proxy пишутся в `tests/api/coverage/test_<тема>.py` с фикстурой `coverage_run`. Примеры точных полей, повторов, ошибок и жизненного цикла находятся в `tests/api/coverage/test_contract.py`.
