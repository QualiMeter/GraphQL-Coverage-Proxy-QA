# Приёмка MVP по ТЗ на PostgreSQL

Для защиты хакатона используйте сценарий `acceptance/mvp/coverage.spec.ts`. Он регистрирует новый сервис, импортирует схему через introspection и создаёт отдельный прогон. Запросы проходят через командный backend в FastAPI + Strawberry. При каждом запуске Python поднимает чистую PostgreSQL и новый процесс demo API. У Анны один заказ на 50. Мутация действительно создаёт второго пользователя.

## Запуск

Из корня QA, в активированном Python-окружении после [установки QA](installation.md), с работающим Docker и Node.js 22:

```sh
python -m pip install -r acceptance/mvp/requirements.txt
npm ci --prefix acceptance/mvp
python -m acceptance.mvp.run
```

Backend берётся из соседней папки по тем же правилам, что остальные тесты. При нескольких копиях задайте `COVERAGE_BACKEND_DIR`. Runner запускает PostgreSQL, применяет миграции, поднимает demo и backend на свободных портах и очищает свой стенд в конце. Для API-сценария достаточно HTTP-клиента Playwright. Для отдельной работы с demo можно запустить `python -m uvicorn acceptance.mvp.demo:app --port 9120` и открыть /graphql на этом порту.

## Что показать за три минуты

Откройте `reports/mvp/<идентификатор>/index.html`. В таблице виден рост hits на каждом шаге и три строки с нулями. Для подробностей откройте связанный отчёт Playwright, выберите тест и откройте вложения с названиями шагов. В каждом записаны идентификатор прогона, сводка сервера и все девять счётчиков. Содержание можно сверить с итоговым `coverage.json` рядом с папкой html.

| Шаг | Результат сервера | Что видно по полям |
|---|---|---|
| Начало | 0/9 | Все hits равны нулю |
| Карточка Анны с заказами | 5/9 · 55.56% | Query.user, User.id, User.name, User.orders, Order.total |
| Создание Maria | 6/9 · 66.67% | Добавляется Mutation.createUser. У User.id и User.name уже по два обращения |
| Повтор карточки | 6/9 · 66.67% | У User.id и User.name по три обращения. Query.users, User.email и Order.id всё ещё имеют ноль |
| Синтаксическая ошибка и неизвестное поле | 6/9 · 66.67% | Для каждой ошибки статус и тело совпадают с прямым ответом Strawberry. Все девять счётчиков прежние |
| Перезапуск backend | Та же сводка и все hits | Python повторно читает завершённый прогон и сравнивает полный ответ. Результат проверки выводится в терминал |

## Соответствие требованиям

| Пункты ТЗ | Где проверяются |
|---|---|
| TST-01, 02 | demo.py и импорт схемы работающего Strawberry. Новый процесс восстанавливает исходные данные |
| TST-03 | coverage.spec.ts создаёт сервис, снимок и прогон. Demo отклонит запрос, если получит любой из двух служебных заголовков |
| TST-04–06 | После каждого действия тест сверяет ответ GraphQL, процент и точные hits по каждой координате |
| TST-07 | Открытый пункт приёмки. Frontend 3868802 загружает реальные сервисы и снимки. После подключения данных прогона нужно выбрать этот же runId в React и сверить процент, цвет узлов и строки таблицы с REST. Для этого потребуется работающий общий стенд |
| TST-08 | Две ошибки сравниваются с прямым ответом upstream в уже заполненном прогоне |
| TST-09 | Уникальные БД и ключ сервиса, завершение прогона в finally, удаление только своего стенда |
| TST-10 | Команды и ожидаемые значения приведены выше. Для отдельного запуска React выполните npm ci и npm run dev в репозитории frontend с COVERAGE_API_PROXY_TARGET, указывающим на локальный backend. Совместная демонстрация React зависит от TST-07 |

Для второго примера откройте [магазин FORMA](../examples/shop/README.md). В QA-сценарии потери ответа покупатель повторяет оформление. Два обращения к мутации видны в журнале, но заказ и списание остатков происходят один раз. Это отвечает на другой вопрос заказчика — что счётчик запросов говорит о реальных действиях покупателей.
